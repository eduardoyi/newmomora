# Feature: Gallery import

**Status:** `done` (continuous model implemented 2026-08-23; pending owner device pass + deploy)
**Last updated:** 2026-08-23
**PRD reference:** [PRD §6.3a Gallery import](../PRD.md#63a-gallery-import--ai-staged-camera-roll-memories)
**Design authority:** [gallery-import design README](../design/gallery-import/README.md) and its pinned Claude handoff. The handoff controls composition, interaction hierarchy, motion, platform manners, accessibility, and state coverage. This document, [the original implementation plan](../plans/gallery-import.md), and [the continuous-model plan](../plans/gallery-import-continuous.md) control product/security/operations.

## Overview

An owner or manager can explicitly ask Momora to look through the photos currently permitted on the originating device, group them into events, and stage AI-curated memory suggestions. Momora never changes the camera roll. It uploads downscaled private previews before review so its vision provider can curate suggestions; only final approval uploads and retains full-resolution originals as ordinary private `media` memories. The feature is device-bound, resumable in the foreground, and opt-in behind client and server admission controls.

**Continuous model (2026-08-23).** The one-shot "start a run, review a batch, start another run later" flow was replaced with a single, open-ended per-family library sweep: one consent unlocks a device-bound driver that keeps producing suggestions in bounded windows for as long as the app is opened, until the library is covered or the user turns it off. See [docs/plans/gallery-import-continuous.md](../plans/gallery-import-continuous.md) for the audit that drove this change and the seam contracts every implementer must honor.

## User-facing behavior

- **One consent, then a background sweep.** The owner/manager sees the trust explainer and OS permission prompt exactly once per device (unless permission is later revoked). From then on, Momora keeps producing suggestions **in the background while the app is open** — there is no "start a new run" action anywhere in the product. The device walks the library window by window (newest photos first, then progressively deeper) until it is covered or the user turns the sweep off.
- **The app-root driver, not a screen, runs the sweep.** `useGalleryImportDriver()` (mounted once in `app/(app)/_layout.tsx`) wires a module-singleton driver (`src/services/gallery-import-driver.ts`) to app launch, `AppState` → active, `NetInfo` reachability changes, and a 60-second tick while there is unsettled work. No screen calls `resumeGalleryImportRunner` itself anymore — screens only *observe* the driver's state (`subscribeGalleryImportDriver`) and the existing live-progress bus, and *kick* it for an out-of-cycle attempt (retry, cellular confirm). A single-flight guard (`isGalleryImportRunnerActive`) keeps the driver from racing the entry screen's own start pipeline when a run has just been created.
- **Re-entry is the timeline activity bell, not a header glyph.** The old `TimelineImportGlyph`/drawer are gone. The activity bell (see [family-activity.md](./family-activity.md)) shows an accent dot when there is an unseen ready batch (tracked per `(runId, readyCount)` pair in `src/utils/gallery-import-bell-seen.ts`, OR'd with the bell's normal unread-activity flag), and the family-activity sheet renders one pinned, non-persisted "N photo suggestions ready to review" row above its sections (or a "still looking"/paused/Wi-Fi-wait line while nothing is ready yet) that opens the review deck or the progress screen. This row is not a `family_activity_events` row — see that doc's Extension guide for why.
- **Settings is a status hub, not a static CTA.** The "Find memories in your photos" Settings row (`GalleryImportSettingsBlock` → `deriveGalleryImportSettingsRow`) reads the same device-bound status as the bell: ready count first ("12 suggestions ready to review" → review), then Wi-Fi wait, then a fair-use pause ("Momora will keep looking tomorrow"), then a driver error, then "still looking" while the sweep is active, then "Suggestions clear in N days" once the review window is expiring soon (≤4 days, unchanged threshold — `GALLERY_IMPORT_EXPIRING_SOON_DAYS`), then the plain "Look through your photos" invitation when nothing has ever started. This replaced a caption bug where a fresh Settings mount always read a stale `useGalleryImport()`-cached `run` as null.
- **The photo invite card appears at 0 or 1 memories, never with more.** `TimelineGalleryImportInvite` renders in the empty-state branch and, once the timeline has exactly one memory, as the first item in the list header — both branches share the one condition `visibleMemories.length <= 1`. Dismissal persists per user+family in AsyncStorage.
- Before the OS ever asks for photo permission, the trust explainer (`GalleryImportTrustExplainer`) states, in three one-line rows, what happens: the phone does the looking and changes nothing, small previews go to Momora to write draft captions (no faces, no location), and only what is kept is saved — the rest clears on its own. **Minimal-copy principle (2026-08-23): reassurance is stated once, on this screen.** A single "Details" link opens one merged sheet (what a preview is, where it goes, how long, what is never sent, you can stop any time) for a parent who wants the honest specifics; every other screen in the flow is eyebrow · title · ≤1 line · buttons, with no boxed explainer duplicating what the trust screen already said. "Not now" is the one real, equal exit — never disabled to nudge a decision, and never duplicated by a second "Cancel."
- The consent screen says what is scanned, that small previews go to Momora and its AI partner, that originals are uploaded only after approval, and that nothing is changed in the camera roll. v1 suggests **photos only**—videos are not silently included.
- iOS/Android permission can be full, limited/selected, denied, or blocked. Each of the three non-full outcomes is a dedicated full screen (`GalleryImportPermissionOutcome`) rather than inline error text: limited shows a "Look through these"/"Choose more photos" choice, denied explains the device Settings path with no scan attempted, blocked opens Settings directly since the OS will not ask again. The permitted corpus is snapshotted before each scan window; choosing more photos applies only to the next window. No location permission is requested and no GPS, filename, raw OS asset ID, face/biometric signal, or identity inference is sent to the server.
- The foreground scanner pages lightweight metadata, groups dated photos with frozen `gallery-v1`, makes 512px JPEG previews, then uploads/dispatches them in bounded chunks within one window at a time (see "Continuous sweep, windows and fair use" below). On iOS it also reads each asset's `mediaSubtypes` (one `Asset.getMediaSubtypes()` call per photo, failure-isolated) and drops screenshots before clustering; Android has no subtype signal in this SDK and admits conservatively (no filtering) instead of guessing. On iOS it uses Expo Media Library's no-download cloud check before URI resolution, so an iCloud-only original is omitted without initiating a download; Android/default assets are treated as local. It prefers Wi-Fi and offers an explicit cellular override, confirmed through a sheet (not a bounce back to the entry screen) that persists the choice onto the checkpoint (`allowCellular`) so the app-root driver honors it on later automatic kicks too.
- **Camera-captures-only corpus (2026-08-11 product decision, unchanged by the continuous model).** "We only care about what pictures people take with the phone" — WhatsApp/iMessage/downloads saves are out of scope. On Android, the scanner resolves the exact-title `'Camera'` album (`MediaLibrary.Album.get('Camera')`, the DCIM camera bucket as a de-facto OEM standard) once at scan start and scopes every query to it; if no `'Camera'` album resolves, or the native Album API itself fails, the scanner falls back to full-library + date-plausibility scanning. iOS has no camera-source signal at all and deliberately keeps the full library. A corpus-mode mismatch between a scan and the stored progressive-deepening frontier resets the frontier rather than mixing coverage across corpora.
- **Fair-use pause, never an error.** The server enforces a rolling 24-hour, per-family `daily_cluster_limit` (default 300 clusters). Once hit, chunk registration is refused with a distinguishable `fair_use` code; the device stops registering new chunks, records `pausedUntil` on the checkpoint, and the driver reports `phase: 'paused_fair_use'`. Every surface that can show this says "Momora will keep looking tomorrow" — never a generic failure message — and the sweep resumes automatically once the window frees (the driver keeps ticking and re-checks; a successful registration also clears a stale pause).
- **The review window extends on activity, not just at run creation.** Any swipe, skip/undo, approval step, or candidate read (`gallery_import_touch_run`, called from the relevant RPCs) bumps the run's `expires_at` — and every live asset/candidate row's own expiry — to now + 30 days, throttled server-side to at most once per day of activity so the review deck's ~9-second poll doesn't turn into a full-table update every call. Settings/the activity row warn once the window is within 4 days of clearing.
- The progress screen (`GalleryImportProgress`) is one number-led layout for every stage instead of a per-stage checklist: an eyebrow naming the stage, the one number that matters ("312 photos read," "40 of 128 previews sent," "3 of 9 batches written · 12 ready," "12 ready to review"), a bar only while genuinely indeterminate (scanning), and a pill reading "Keep Momora open" (scanning/preparing) or "Safe to close" (everything else, including waiting/uploading/reviewing). It never drives the runner itself anymore — it only observes the driver state, the live-progress bus, and its own ~8s run poll, and kicks the driver for a retry or a cellular confirmation.
- **Two distinct stop actions**, replacing the old single "Stop": **"Stop looking for more"** turns off `autoContinue` on the frontier (`setGalleryImportAutoContinue`) — Momora finishes whatever chunk work is already in flight and then stops extending to further windows, but every suggestion already made stays reviewable. **"Stop and clear"** is the original destructive cancel (drafts clear, kept memories stay), behind its own confirm sheet.
- A run that finds nothing (yet) gets one of three distinct calm screens (never a generic error): nothing stood out among readable photos, no dated photos on this device at all, or nothing yet from a limited-access grant (with a path to choose more photos). A sweep that stops for a reason outside the user's control — a lapsed subscription, a demoted role, offline, a transient hiccup, or an unrecoverable failure — gets its own distinct copy.
- Suggestions appear in a read-only deck that keeps refilling as further windows land. Keep proceeds to a composer where caption, date, tags, and the selected photos can be edited; Set aside is a recoverable in-run skip. No card is auto-approved or automatically resurfaced later. "N more coming"/"more on the way" is derived from server pending count + local unsettled clusters + whether the frontier says more history remains (`deriveGalleryImportComingIndicator`), never from a stale local plan — see "Continuous sweep, windows and fair use" below. The deck's "done" state (offering Finish, which calls `complete-gallery-import-run`) only appears once that indicator says `{ kind: 'none' }` — genuinely nothing left, ever. Another device is told to continue on the device that scanned the photos, without previews, device name, or counts.
- Approval is checkpointed before original upload. Relaunching with an uploading/finalizing outbox returns directly to that locked composer and resumes once; a failed outbox waits for an explicit retry that reuses its lease. If the server committed `begin-gallery-import-approval` but the client timed out before checkpointing its response, the server's `approving` candidate routes back to the composer, idempotently recovers the stable lease, and does not create or edit a second memory.
- A locked approval recovery has no editable inputs, so its pinned safe-area footer deliberately bypasses keyboard translation. This keeps Retry saving in the native accessibility frame while the normal editable composer retains keyboard-sticky behavior.
- Final approval creates one `memory_type='media'` memory with `creation_source='gallery_import'`, its selected original assets, optional tags, and (when supplied by curation) its emotion. It never generates an illustration. Normal photo limits still apply: 1–10 assets; originals may be JPEG/PNG/HEIC/HEIF/WebP and are limited to 20 MiB each.
- Family members receive one generic timeline digest after **30 minutes of no new gallery approvals**. Every new approval restarts that quiet period. The notification intentionally omits candidate/memory IDs and counts.

### Continuous sweep, windows and fair use

Replaces the old "exact launch limits" model (a capped run of at most 60 candidates, admitted twice in the first 30 days then once a month). There is no longer a cap on how many windows a family's sweep can produce over its lifetime — admission now only enforces **at most 4 concurrently active runs per family** (runs are device-bound, so each family device gets its own sweep; 2026-08-23 follow-up migration `20260823210000`) and a rolling fair-use ceiling:

- **Window** = one scan pass producing at most `GALLERY_IMPORT_WINDOW_CLUSTERS` (60) clusters, chunked `GALLERY_IMPORT_CLUSTERS_PER_CHUNK` (4) clusters per chunk (chunk ordinals continue across windows within the one run). A new window is only planned once every existing chunk has settled (`dispatched` or `abandoned`), the backlog (server `readyCandidates` + `pendingClusters` + local unsettled clusters) is below `GALLERY_IMPORT_TARGET_BACKLOG` (120), the frontier says more history exists, `autoContinue` is on, and no fair-use pause is active (`maybeExtendGalleryImportPlan` in `gallery-import-runner.ts`).
- **Contiguous frontier.** Within a window that continues a prior frontier: Phase A (newer than `coveredThroughNewestMs`) enumerates **ascending** and admits its **oldest** groups first, up to the window size; the remaining window is filled from Phase B (older than `oldestCoveredMs`), which enumerates and admits **newest-first**. A first-ever scan (no frontier yet) is newest-first, unchanged. This keeps the covered range gapless — Phase A's ascending enumeration means a truncated/early-stopped catch-up pass only ever leaves a gap at the newest end (which the next Phase A picks straight back up), never an unexamined band adjacent to the frontier.
- **Early-stop enumeration.** Each phase stops paging once `targetClusterCount + 1` *complete* clusters have formed (a group closed by a confirmed >3h gap), rather than always walking the full `GALLERY_IMPORT_MAX_ENUMERATED_ASSETS` (4,000) budget — this bounds how many native pages one window needs.
- **Pass deadline pauses, never drops.** The five-minute preparation budget (`GALLERY_IMPORT_PREPARATION_BUDGET_MS`) only stops *starting* new native work; a chunk not fully prepared when the deadline hits stays in its current status (`planned`/`registered`/`uploaded`) for the next driver pass to continue. Upload time is never counted against this deadline.
- **Chunk attempts, classified.** A chunk that is refused or throws is marked `failed` and retried on the next pass, up to `GALLERY_IMPORT_CHUNK_MAX_ATTEMPTS` (3), **but only a genuine server refusal or a distinguishable local-consistency bug counts against that budget** (`errorCountsAsAttempt`). A transport/connectivity hiccup with no HTTP code, the Edge Function's own `'timeout'` (from the 45s `GALLERY_IMPORT_EDGE_TIMEOUT_MS` round-trip budget), or the raw preview PUT's `'upload_timeout'` never spends an attempt — three kicks during a bad-connection stretch must not permanently abandon an otherwise-healthy chunk.
- **Abandoned chunks are an accepted coverage hole.** Once a chunk exhausts its attempts it becomes `abandoned` — terminal locally, excluded from every "N coming" indicator, and shown to the user as a muted "N batches couldn't be sent" line. The frontier treats an abandoned chunk as *settled* (so the sweep keeps moving forward instead of looping on the same window forever), which means the photos inside it are never actually examined by this pass. This is a deliberate, documented trade-off — see the continuous plan's "Risks / accepted limitations."
- **Fair use**: `daily_cluster_limit` (smallint, default 300, 20–5000) caps clusters registered per family in a rolling 24 hours, checked in `register_gallery_import_chunk` against `gallery_import_cluster_results.created_at`. Exceeding it raises a distinguishable `P0002` (with an ISO-timestamp hint for exactly when enough rows age out) that the Edge maps to HTTP 429 `{ code: 'fair_use', retryAfterSeconds }`; the client treats this as a pause (`GalleryImportFairUsePausedError`), never an error.
- **Admission** = paid write access, owner/manager role, and **at most 4 concurrently active device-bound runs per family** — the old first-30-days/normal-monthly run caps are gone entirely (`create_gallery_import_run_internal` no longer reads `initial_run_limit`/`normal_monthly_run_limit`, though those columns remain in the schema).
- The per-run **limit template** was widened for a whole-library sweep instead of a capped batch: `maxChunksPerRun` 1–5000 (default 2000), `maxAssetsPerRun` 1–100000 (default 50000), `maxAssetsPerChunk` 1–500 (default 100), `maxCandidatesPerRun` 1–10000 (default 5000); `maxProviderAttemptsPerCluster`/`maxImagesPerCluster`/`maxPreviewBytes` are unchanged (3 / 10 / 1,500,000). Widening the template bumps `policy_epoch`, but every in-flight run keeps its own immutable `limit_snapshot`.
- The foreground scanner still pages at 100, considers at most 4,000 assets per scan pass (`GALLERY_IMPORT_MAX_ENUMERATED_ASSETS`), and groups across a 3-hour gap (`GALLERY_IMPORT_CLUSTER_GAP_MS`) — unchanged from before the continuous model.

## Architecture

```mermaid
sequenceDiagram
  participant Drv as App-root driver
  participant D as Origin device
  participant E as Supabase Edge Functions
  participant R as Private Cloudflare R2
  participant W as GalleryImportWorkflow
  participant O as OpenAI gpt-4o-mini

  Drv->>Drv: launch / AppState active / NetInfo change / 60s tick
  Drv->>D: single-flight kick (skips if the start pipeline is already active)
  D->>D: Permission snapshot, one window's metadata scan, cluster, checkpoint
  D->>E: Create/continue admitted run
  E-->>D: Run capability, limits, chunks[], pendingClusters, fairUse
  D->>D: Serially make previews; omit unavailable/corrupt assets
  D->>E: Register bounded chunk manifest (429 fair_use if daily cap hit)
  E-->>D: Required accepted tokens/suppressed clusters
  D->>E: Request PUT URLs only for accepted previews
  D->>R: PUT transient 512px JPEG previews
  D->>E: HEAD-verified dispatch (unavailableAssetTokens for post-admission losses)
  E->>W: HMAC-authenticated {chunkId, attempt}
  W->>E: Timestamped HMAC bridge: private chunk input (plain await, never a Workflow step)
  W->>E: get_gallery_chunk_input excludes unavailable assets
  W->>O: One bounded vision request per cluster, isolated per cluster (step.do, no retries)
  W->>E: Idempotently publish per-cluster results; fail_gallery_cluster on a definite single-cluster failure
  W->>E: Scrub content-bearing chunk input
  D->>E: Capability-bound review actions / approval lease
  D->>R: PUT originals only after approval
  D->>E: HEAD-verified atomic finalization
  E->>E: Hourly cron reconciles stale dispatched/processing chunks (claim_stale_gallery_chunks) and re-dispatches with an attempt-suffixed Workflow id
```

The device alone keeps the opaque-token → OS-library-ID mapping in an authenticated, user/family/run-scoped AsyncStorage checkpoint. Postgres, R2 keys, analytics, logs, prompts, and Workflow state never receive raw OS identifiers. The run capability is high-entropy, stored only in that checkpoint, and hashed server-side; it is required alongside the caller JWT and exact-family role check for run/candidate/approval operations.

**The app-root driver (`src/services/gallery-import-driver.ts`)** is the only caller of `resumeGalleryImportRunner`. `useGalleryImportDriver()` mounts it exactly once, in `app/(app)/_layout.tsx`, and wires it to `AppState` (`active` → kick), `NetInfo` (any change → kick, so Wi-Fi regain resumes automatically), and a `GALLERY_IMPORT_DRIVER_TICK_MS` (60s) interval that runs only while a checkpoint has unsettled chunks or more history to sweep. It is single-flight per (userId, familyId): a burst of overlapping kicks coalesces into exactly one follow-up attempt, and it defers entirely to the entry screen's own `beginGalleryImportPipeline` start pipeline while that pipeline has already marked the run active (`isGalleryImportRunnerActive`), so the two never process the same chunks concurrently. A driver-caught error (as opposed to a `waiting_wifi`/`paused_fair_use` classified pause) schedules its own automatic retry on an exponential backoff (30s → 5min), reset on the next success.

**The `pendingClusters` fix.** `countPendingGalleryClusters` (`supabase/functions/_shared/gallery-import.ts`) previously selected a non-existent `id` column on `gallery_import_cluster_results` (its primary key is the composite `(chunk_id, cluster_signature)`); PostgREST rejected every request with a 400 that the surrounding `try/catch` silently turned into `null`, so `pendingClusters` was always unknown in production and the deck could never honestly know it was done. It now selects `chunk_id`.

**Server reconciliation cron.** The hourly `cleanup-gallery-imports` cron now also calls `redispatchStaleGalleryChunks`, which claims chunks stuck `dispatched`/`processing` for more than 20 minutes (`claim_stale_gallery_chunks`, run non-terminal and not expired) and re-dispatches each under a fresh, attempt-suffixed Workflow instance id (`gallery:${chunkId}:${attempt}`) so a re-dispatch can never collide with (or be silently deduplicated against) a prior stuck/ambiguous instance. A chunk that has already exhausted 3 dispatch attempts is instead failed directly (`fail_gallery_chunk(id, 'GALLERY_RECONCILE_EXHAUSTED')`) rather than claimed again.

**Per-cluster worker isolation.** `GalleryImportWorkflow.run` runs each cluster as its own no-retry `step.do` (4-minute timeout). A definite single-cluster failure (a vision refusal/malformed response the corrective retry couldn't fix, an exhausted attempt cap, an invalid preview) calls `fail_gallery_cluster` for that cluster only and the Workflow continues with the rest of the chunk; only a whole-chunk structural failure (bad chunk input) still fails the entire chunk. An *ambiguous* failure (a possibly-paid provider call whose outcome could not be confirmed) still aborts the whole Workflow instance so the reconciliation cron above can safely re-dispatch a fresh attempt. `getGalleryChunkInput` is deliberately **not** a Workflow step — it is a plain `await`, because a step's return value is persisted in Workflow history for replay, and the chunk input carries preview keys, caption instructions, and cluster signatures that must never enter that history.

**Asset unavailability (S3).** An asset the device admitted at registration but can no longer produce a preview for (deleted, iCloud-only original, permission revoked mid-sweep) is reported at dispatch time as `unavailableAssetTokens` rather than failing the whole chunk. The server marks it `unavailable_at` (only while its preview was never actually uploaded — a verified manifest stays immutable), recomputes the chunk's counts, and resolves any cluster left with zero available assets as an `invalid_preview` skip (no suppression receipt, so it can still be offered on a later sweep if the asset becomes available again). A chunk left with nothing available closes `completed` without ever dispatching.

**Completion guards.** `complete_gallery_import_run` now also refuses while any chunk is `registered|uploading|dispatched|processing` (not only while candidates are staged/posting), and `publish_gallery_candidates`/`publish_gallery_cluster_result` now also refuse into an already-`completed` run (matching cancelled/expired/failed) — closing two races where a run could complete with work still in flight, or a straggling Workflow could publish into a run the family had already finished reviewing.

## Data model

| Table / prefix | Role and retention |
|---|---|
| `memories.creation_source` | Server-owned provenance: `manual`, `onboarding`, or non-displayed `gallery_import`. |
| `families.gallery_caption_language`, `gallery_caption_instructions` | Owner-only BCP 47 caption locale and sanitized optional instructions (≤500 chars). |
| `gallery_import_admission_settings` | Singleton server kill switch/admission/TTL/quiet-period and immutable per-run-limit source. Continuous model adds `daily_cluster_limit` (smallint, 20–5000, default 300) — the rolling 24h per-family fair-use cap — and widens `limit_template`'s validated ranges (see "Continuous sweep" above). The `normal_monthly_run_limit`/`initial_run_limit`/`initial_window` columns remain in the schema but are no longer read. |
| `gallery_import_runs`, `chunks`, `assets`, `cluster_results` | Device-bound run, immutable manifest, preview receipts, and terminal cluster ledger. Review TTL defaults to 30 days (constrained to 1–90 days) **from last activity, not from run creation** (`gallery_import_touch_run`, throttled to at most once per day of activity); a due completed run becomes `expired` only when fenced cleanup claims its transient objects. `chunks` adds `dispatch_attempts` (smallint, default 0, incremented on every (re)dispatch) for reconciliation; the `processing → dispatched` transition is now valid so a stuck chunk can be re-marked for a fresh Workflow instance. `assets` adds `unavailable_at` (nullable timestamptz) for S3. |
| `gallery_import_candidates`, `cluster_receipts` | Staged drafts and best-effort future suppression, without raw photo IDs or visual fingerprints. Candidate caption is replaced on expiry. |
| `gallery_import_provider_attempts` | Private attempt/usage/error audit. A network/timeout outcome is `ambiguous` and is not automatically replayed; an existing `ambiguous` row at a requested ordinal now correctly returns `denied` on `reserve_gallery_attempt` (see below) instead of erroring. |
| `gallery_import_approval_leases` | Stable memory ID and exact original keys for idempotent approval/finalization. |
| `gallery_import_digest_windows` | Per family/actor 30-minute quiet-period aggregation. After a sent window resets to zero, the next approval restores both timestamps and starts a fresh quiet period while preserving any active claim fence. |
| `gallery_import_workflow_bridge_nonces` | 10-minute HMAC replay protection. |
| `{userId}/gallery-import/{runId}/previews/{assetToken}.jpg` | Private transient preview; deleted by fenced cancel/expiry cleanup. |
| `{userId}/memories/{memoryId}/media/{assetId}.{ext}` | Private approved original; retained as normal journal media until its memory/account/family is deleted. |

All gallery tables use RLS with no direct client table policies. Client reads and mutations go through capability-bound security-definer RPCs and authenticated Edge Functions. Approval finalization is the only route that writes gallery provenance/originals into normal memory tables. Family/account cascade and cleanup delete unapproved server objects but never touch the device library or already-approved journal media.

## API, RPCs, Edge Functions, and Worker

All user endpoints require a non-anonymous JWT, paid write access where mutation requires it, owner/manager authorization for the specified live family, and the run capability where a run/candidate is involved. Closed error codes are returned; no content-bearing values are logged.

| Endpoint | Call order / responsibility |
|---|---|
| `create-gallery-import-run` | Creates an admitted run from `familyId`, algorithm/consent versions, and permission mode; returns server limits and a one-time run capability. Admission no longer checks a first-30-days or monthly run cap — only the ≤4 concurrently-active-runs-per-family cap (one sweep per device). |
| `register-gallery-import-chunk` | Validates the bounded cluster/token/date/dimension/favorite manifest after locally unavailable/corrupt assets are omitted, then returns required `acceptedAssetTokens` and `suppressedClusterSignatures` before upload. Once the family's rolling 24h `daily_cluster_limit` would be exceeded, responds `429 { code: 'fair_use', retryAfterSeconds }` instead — the device treats this as a pause, never an error. |
| `get-gallery-import-upload-url` | Server chooses the exact preview key and returns a short-lived PUT URL with signed JPEG metadata headers including hash, bytes, and dimensions. |
| `dispatch-gallery-import-chunk` | HEAD-verifies every still-available preview/metadata receipt, freezes the chunk, then HMAC-dispatches `{ chunkId, attempt }` to the Worker. Accepts an optional `unavailableAssetTokens` field (S3) — assets admitted at registration the device can no longer produce a preview for; the server drops them from the manifest and, if that empties the chunk, closes it `completed` and returns `{ accepted: true }` without ever dispatching. |
| `get-gallery-import-run`, `get-gallery-import-candidates` | Capability-bound status/candidate reads; candidate preview URLs are private, short-lived (5 minutes). The run response additionally carries `chunks: { ordinal, status }[]`, `pendingClusters` (now correctly computed — see the Architecture note above), `liveCandidateAssetTokens`, and `fairUse: { pausedUntil }`. |
| `set-gallery-import-candidate-skip`, `update-gallery-import-candidate` | In-run skip/undo and composer edits. Edited assets must be selected from that candidate’s cluster; caption is 1–1,000 chars and a candidate has 1–10 assets. The Worker’s vision draft cap is 480 characters. |
| `begin-gallery-import-approval` | Rechecks access and reserves a stable memory ID, lease, and exact original-key manifest. |
| `get-gallery-import-approval-upload-url`, `record-gallery-import-approval-upload`, `finalize-gallery-import-candidate` | Resolve originals locally; server-chosen PUT URL; R2 HEAD/receipt; then one atomic RPC to create memory/media/tags/provenance, receipts, and digest window. |
| `cancel-gallery-import-run`, `complete-gallery-import-run` | Capability-bound terminal controls. `complete-gallery-import-run` additionally refuses while any chunk is `registered|uploading|dispatched|processing`, not only while candidates are staged/posting. Cancellation/expiry clears local checkpoint/cache and fenced cleanup deletes unapproved objects. |
| `get-gallery-caption-settings`, `update-gallery-caption-settings` | Owner-only caption locale/instruction retrieval and autosave. |
| `cleanup-gallery-imports` | Cron-secret-only hourly cleanup and bridge-nonce pruning. Any due run, including a completed run, becomes `expired` as the deletion fence; object delete failures keep that fence open for retry. Also calls `redispatchStaleGalleryChunks` after expiry work (see Architecture). Finalized original media, memories, and approved receipts remain excluded/preserved. |
| `send-gallery-import-digests` | Cron-secret-only, every five minutes; claims windows quiet for 30 minutes and sends one privacy-filtered timeline digest using notification preferences/block rules. |
| `workflow-gallery-import-bridge` | Narrow timestamped HMAC bridge with nonce protection for Worker input, attempt leasing/usage, publication, per-cluster and whole-chunk failure (new `fail_gallery_cluster` op), and scrub operations. Error mapping is now precise: only Postgres `P0001`/`22023`/`42501`/`28000` map to the existing non-retryable 409 `bridge_rejected`; every other error (deadlock `40P01`, statement timeout `57014`, connection-class `08xxx`, resource-class `53xxx`, or anything unexpected) maps to a retryable 503 `bridge_unavailable`. It does not expose a Supabase service-role key to Cloudflare. |

`GalleryImportWorkflow` in `cloudflare/memory-illustration-worker` drops assets that duplicate an earlier asset's expected byte hash within a cluster (exact-hash only, not perceptual dedup), validates private preview bytes/type/dimensions, processes at most ten images per cluster, and calls `gpt-4o-mini` with a schema-constrained multi-image request. The prompt instructs the model to prefer meaningful people photos, select for variety across the cluster's arc, exclude screenshots/screens/documents/receipts/food-only shots, stage a single-photo cluster only when it clearly stands alone, and return zero groups ("silence beats a bad card") for a mundane/utilitarian cluster or when uncertain. One cluster may split into at most three groups and may never merge with another cluster. A closed `DEFAULT_GALLERY_MIN_CONFIDENCE` (0.6) gate then drops any returned group below that score before publication; a cluster whose groups are all dropped this way publishes as a `low_confidence` skip instead of staging a weak card. It stores only scalar Workflow-step outputs: previews, prompts, model responses, semantic descriptions, and captions do not enter Workflow history/logs. Definite retryable provider failures may use the bounded attempt cap; an ambiguous network/timeout/disconnect is quarantined and requires reconciliation/manual retry rather than an automatic possibly-billed replay. Each cluster now runs as its own isolated Workflow step (see Architecture) — a single bad cluster no longer fails the whole chunk.

## Extension guide

**Safe to extend**

- **Adding a driver trigger.** To make the sweep react to a new lifecycle signal, add a listener inside `startGalleryImportDriverListeners()` (`src/services/gallery-import-driver.ts`) that calls `kickGalleryImportDriver('your-reason', opts?)` — the reason string is only used for readability/coalescing logs, never branched on. The single-flight guard and the pending-kick coalescing already handle overlap; you do not need to add your own guard.
- **Changing the window size or backlog target.** `GALLERY_IMPORT_WINDOW_CLUSTERS`, `GALLERY_IMPORT_CLUSTERS_PER_CHUNK`, and `GALLERY_IMPORT_TARGET_BACKLOG` (`src/constants/gallery-import.ts`) are the three knobs that shape the sweep's cadence. Raising the window size increases per-pass native/upload work; lowering the backlog target makes the deck refill more eagerly (more windows, sooner) at the cost of more chunk/dispatch overhead. Neither changes `gallery-v1` signatures or clustering — only how much of one scan pass gets admitted.
- **Never let a screen resume the runner.** Only `gallery-import-driver.ts` may call `resumeGalleryImportRunner`/`startGalleryImportRunner`. A screen that adds its own resume-on-mount effect will race the driver's single-flight guard and can double-process the same chunks — this is exactly the bug the continuous-model rewrite removed from `gallery-import-progress.tsx`. A screen should only ever `subscribeGalleryImportDriver`, read the live-progress bus, and call `kickGalleryImportDriver` for an explicit user-triggered retry.
- **Never make chunk input a Workflow step output.** `getGalleryChunkInput` (`cloudflare/memory-illustration-worker/src/gallery-workflow.ts`) is a plain `await`, not a `step.do`, specifically because a step's return value is persisted in Workflow history for replay — and the chunk input carries preview keys, caption instructions, and cluster signatures that must never enter that history. `bridgeRetry` already bounds its own retries and the fetch is idempotent (`get_gallery_chunk_input` only returns still-pending clusters), so a plain await is safe here. Keep any future whole-chunk fetch this way too.
- **Abandon → best-effort dispatch with unavailable tokens.** When a chunk is about to be abandoned (attempts exhausted) and it was already registered server-side (has a `chunkId`), `processGalleryImportChunks`'s `failChunk` makes one best-effort `dispatchGalleryImportChunk` call reporting every not-yet-uploaded token as `unavailableAssetTokens` before marking the chunk abandoned locally. This prevents a registered-but-abandoned chunk from leaving its server row `uploading` with pending `cluster_results` forever (which would over-count `pendingClusters` and block `complete_gallery_import_run`). The call's failure is swallowed — the reconciliation cron (`claim_stale_gallery_chunks`) is the backstop if it also fails. Follow this pattern for any new terminal-on-the-client-but-registered-on-the-server transition.
- The day-pool photo chooser is wired: `GalleryImportApproval`'s `onAddPhotos?: (context: GalleryImportAddPhotosContext) => void` seam (`src/components/gallery-import/gallery-import-approval.tsx`) hands the current selection context to the route (`app/(app)/gallery-import/approve.tsx`), which opens `GalleryImportPhotoChooser` (`src/components/gallery-import/gallery-import-review-sheets.tsx`) in select mode over the candidate's reconstructed cluster pool (`buildGalleryImportDayPool` in `src/utils/gallery-import-deck.ts`). The pool is limited to server-admitted cluster assets — anything else would fail `update-gallery-import-candidate`'s cluster check. From the read-only review deck the same sheet opens in browse mode.
- Add a locale through the shared caption-locale registry (`src/constants/gallery-caption-locales.ts`), preserving owner-only autosave and server BCP-47 validation. Two lists live there: `galleryCaptionLocaleTags` (241 entries — the full accepted/validated set; `normalizeGalleryCaptionLocale` and the Edge Function's BCP-47 shape check both key off this, unchanged by curation) and `curatedGalleryCaptionLocaleTags` (48 entries — 2026-08-10 product decision; presentation-only, what the picker actually browses/searches). Adding a language: give it a real `{ en, native }` pair in `GALLERY_CAPTION_LOCALE_NAMES` (never rely on `Intl.DisplayNames` as the source of truth — Hermes on-device silently echoes the input tag back instead of throwing when it lacks ICU data for a locale, unlike Jest's full-ICU Node runtime); add it to `curatedGalleryCaptionLocaleTags` only if it should actually appear in the picker.
- Add aggregate, scalar, content-free analytics only through the typed catalog in `src/services/analytics.ts` and [analytics.md](./analytics.md).
- Tune admission only through the server settings and a new benchmark/decision record; preserve immutable run snapshots and the client/server caps.

**Do not change without coordinated contract/privacy review**

- Do not use a generic upload URL or accept client-chosen import keys. Preview and original PUTs must stay run/lease-bound and be HEAD-verified.
- Do not persist OS asset IDs, file names, GPS, face/identity results, prompts, model output, image-derived descriptions, or unapproved preview bytes outside their private short-lived path.
- Do not treat limited/selected access as full-library access, silently add later-granted photos, or claim work continues after app process death — "Safe to close" means checkpointed resume, not background continuation past process death.
- Device-local availability detection, URI resolution, and serial preview conversion share a 30-second per-photo deadline and a five-minute absolute preparation budget per driver pass; each attempt receives the smaller remaining duration. The budget begins immediately before chunk preparation. Once exhausted, no additional native asset work starts — a chunk not fully prepared stays in its current unsettled status for the next pass; it is never closed as if it had dispatched. Each preparation attempt has a unique device-local cache filename, so late native completion is deleted without touching a newer retry; these local keys never enter manifests, uploads, or checkpoints.
- Resume reconciles server state before doing any further chunk work. A run at `reviewing` is **not** terminal for admission — chunks keep registering/uploading/dispatching for as long as the run itself is non-terminal; only the local checkpoint's status *label* is synced to `reviewing` for display purposes. (This reverses the original 2026-08-10 design, which treated `reviewing` as terminal for admission.)
- Original resolution, upload URL requests, PUTs, receipts, and finalization use a 30-second per-step deadline and a two-minute foreground approval budget per attempt. Approval deliberately skips discovery's local-only cloud preflight: keeping a memory is an explicit request for PhotoKit to retrieve its selected iCloud originals, while the deadline keeps that foreground download bounded. Missing/deleted originals still fail, and a late iCloud retrieval can make the explicit retry succeed. The composer shows content-free per-photo progress. A timeout leaves the stable lease/outbox retryable; automatic recovery runs once, while a failed attempt requires an explicit retry. Finalization and local outbox removal are idempotent, including a late result from an earlier timed-out native operation.
- Approval diagnostics expose only the current content-free stage—preparing, requesting a secure upload, uploading, confirming, or finalizing—and a test-addressable error. A `recorded:false` receipt is a failed confirmation, never treated as permission to finalize.
- Native presigned PUTs use Expo FileSystem's foreground URLSession. This keeps iOS PhotoKit full-size file URLs in the app process that resolved them and matches the product promise that uploads pause rather than continue after the app closes.
- Do not auto-approve, use a per-memory notification fan-out, make candidates cross-device, include video/GPS/face recognition, or replay an ambiguous provider call.
- Changing the algorithm/signature/caps/vision model/retention needs migration and Worker/Deno/client/pgTAP coverage plus updates to this doc, TECH_SPEC, privacy/store copy, and the rollout record.
